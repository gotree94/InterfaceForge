# ROS2 TurtleBot3 1m 이동 명령 가이드 — Odometry · EKF · ICD · Isaac Sim 확장

> TurtleBot3 Burger 1m 전진 → Odometry 해석 → EKF 센서 융합 → ICD 개념 → Isaac Sim Sim2Real 확장

---

## 1. TurtleBot3 1m 전진 명령

### 1.1 TurtleBot3 구동

TurtleBot3 Burger는 ROS2 기반 모바일 로봇으로, `diff_drive_controller`가 `cmd_vel` 토픽을 받아 좌/우 바퀴 속도로 변환합니다.

```bash
# TurtleBot3 1m 전진 (선속도 0.2 m/s, 5초 = 1m)
ros2 topic pub --once /cmd_vel geometry_msgs/Twist \
  '{linear: {x: 0.2, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}'
```

5초 후 정지:
```bash
ros2 topic pub --once /cmd_vel geometry_msgs/Twist \
  '{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}'
```

### 1.2 `geometry_msgs/Twist` 메시지 구조

```
Vector3 linear       # m/s
  float64 x          # 전/후
  float64 y          # 좌/우 (옆으로 미끄러짐)
  float64 z          # 상/하
Vector3 angular      # rad/s
  float64 x          # Roll
  float64 y          # Pitch
  float64 z          # Yaw
```

TurtleBot3는 diff-drive이므로 `linear.x` (전진) + `angular.z` (회전)만 사용합니다.

## 2. Odometry — `/odom` 토픽

### 2.1 Open-loop vs Closed-loop

위 명령은 **open-loop**입니다. 바퀴가 미끄러져도 로봇은 "명령대로 갔다"고 믿습니다. 실제로는:
- 바닥 재질에 따른 slip
- 타이어 공기압 차이
- 배터리 전압 강하 → 모터 토크 변화

→ **Odometry 피드백**이 필요합니다.

### 2.2 `nav_msgs/Odometry` 메시지 구조

```yaml
std_msgs/Header header
  uint32 seq
  timestamp stamp          # 데이터 생성 시각
  string frame_id          # "odom"
string child_frame_id      # "base_footprint"

geometry_msgs/PoseWithCovariance pose
  Pose pose
    Point position         # x, y, z (m)
    Quaternion orientation # x, y, z, w
  float64[36] covariance   # 6x6 공분산 행렬

geometry_msgs/TwistWithCovariance twist
  Twist twist              # 선속도 + 각속도
  float64[36] covariance
```

### 2.3 Dead Reckoning의 한계

Odometry는 **wheel encoder**만으로 위치를 추정합니다.

**문제점**:
| 현상 | 영향 |
|---|---|
| 바퀴 slip | 위치 오차 누적 (drift) |
| Uneven terrain | pitch/roll 정보 없음 |
| 오랜 주행 | unbounded error growth |

**해결**: 추가 센서(IMU, GPS, magnetic heading)를 **EKF**로 융합

## 3. EKF (Extended Kalman Filter)

### 3.1 robot_localization 패키지

```bash
sudo apt install ros-humble-robot-localization
```

### 3.2 EKF 파라미터 상세 해설

```yaml
# ekf.yaml
ekf_filter_node:
  ros__parameters:
    # === 프레임 설정 ===
    world_frame: world           # 전역 좌표계 (GPS 사용 시 "world", 실내는 "odom")
    odom_frame: odom             # odometry 좌표계
    base_link_frame: base_link   # 로봇 본체 좌표계
    map_frame: map               # SLAM map (선택)
    
    # === 시간 설정 ===
    frequency: 50.0              # EKF 업데이트 주파수 [Hz]
    two_d_mode: false            # false = 3D (roll/pitch/z 포함), true = 2D 평면
    
    # === 센서 입력 설정 ===
    # odom0: wheel odometry
    odom0: /odom
    odom0_config: [true, true, false,    # x, y, z position
                   false, false, true,    # roll, pitch, yaw
                   true, false, false,    # vx, vy, vz
                   false, false, true,    # vroll, vpitch, vyaw
                   false, false, false]   # ax, ay, az
    odom0_differential: false     # false = 절대 측정, true = 상대 델타
    odom0_relative: true          # true = 초기 위치 무시 (차분만 사용)
    odom0_queue_size: 5
    
    # imu0: IMU 센서
    imu0: /imu/data
    imu0_config: [false, false, false,   # x, y, z (IMU는 position 못 줌)
                  true, true, true,       # roll, pitch, yaw ← orientation
                  false, false, false,    # vx, vy, vz
                  true, true, true,       # angular velocity
                  true, true, true]       # linear acceleration
    imu0_differential: false
    imu0_relative: true
    imu0_queue_size: 5
    
    # gps0: GPS 수신기 (선택)
    gps0: /gps/fix
    gps0_config: [true, true, false,     # x, y, z
                  false, false, false,    # roll, pitch, yaw
                  false, false, false,    # vx, vy, vz
                  false, false, false,    # vroll, vpitch, vyaw
                  false, false, false]    # ax, ay, az
    gps0_differential: false
    gps0_relative: true
    gps0_queue_size: 5
    
    # === 상태 벡터 출력 ===
    publish_tf: true              # odom→base_link TF 발행
    print_diagnostics: true       # 진단 메시지 출력
```

### 3.3 fusion 동작 방식

```
                    ┌──────────────────┐
  /odom ──────────►│                  │
  (wheel enc.)     │                  │
                    │    EKF Node      │──► /odometry/filtered (Pose+Twist)
  /imu/data ──────►│  (robot_local-   │──► /odom → /base_link TF
  (IMU)            │   ization)       │
                    │                  │
  /gps/fix ───────►│  ʷˣ = f(ʷˣ, u)  │
  (GPS)            │  z = h(ʷˣ)       │
                    └──────────────────┘
```

**EKF가 하는 일**:
1. **예측 단계**: IMU 가속도/각속도로 상태 예측 (50 Hz)
2. **갱신 단계**: Odometry/GPS가 들어오면 correction (각 센서 rate에 따라)
3. **센서 간 보완**:
   - IMU: 단기 고속 drift 보정, roll/pitch 절대값 제공
   - Wheel odometry: 저주파 위치 안정성
   - GPS: 장기 위치 drift 제거 (실외)

### 3.4 covariance의 의미

`covariance[36]`는 6x6 행렬을 row-major로 편 것입니다:

```
Position:     x     y     z     roll  pitch yaw
    x       [c00   c01   c02   c03   c04   c05]
    y       [c06   c07   c08   c09   c10   c11]
    z       [c12   c13   c14   c15   c16   c17]
    roll    [c18   c19   c20   c21   c22   c23]
    pitch   [c24   c25   c26   c27   c28   c29]
    yaw     [c30   c31   c32   c33   c34   c35]
```

값이 클수록 = 센서 불확실성 큼 → EKF가 해당 센서를 덜 신뢰함

## 4. ICD (Interface Control Document)

### 4.1 ICD가 왜 필요한가

TurtleBot3는 단순합니다: `cmd_vel → diff_drive → wheel encoder → /odom`

**드론 시스템**은 훨씬 복잡합니다:

| 구성 요소 | 인터페이스 | 프로토콜 |
|---|---|---|
| Flight Controller (Pixhawk) | UART | MAVLink |
| GPS+Compass | I2C | UBX |
| LiDAR | USB/UART | Serial |
| Camera (Gimbal) | Ethernet | RTSP/UDP |
| ESC x4 | PWM/DShot | 50-500 Hz |
| Companion Computer | UART/USB | MAVLink ↔ ROS2 |

→ **ICD = 모든 인터페이스를 정의한 단일 문서** (SSOT)

### 4.2 ICD가 정의하는 것

| 항목 | 내용 | 예시 |
|---|---|---|
| Message | 데이터 구조 | ControlCmd (16 bytes) |
| Signal | 개별 필드 | thrust: uint16, 1000-2000 |
| Bus | 물리 전송 | CAN_HIGH (1 Mbit/s) |
| Equipment | 송/수신 주체 | FC → ESC1 |

### 4.3 ICD의 ROS2 개발 이점

1. **인터페이스 우선 설계**: 코드보다 메시지 구조가 먼저 정의됨
2. **자동 생성**: `.msg` 파일을 ICD에서 자동 생성 → 오류 방지
3. **Sim↔Real 일관성**: 동일 메시지 사용 → 전환 비용 최소화
4. **문서 자동화**: ICD → DDS IDL → HTML 문서 자동 생성

## 5. TurtleBot3 → Drone → Isaac Sim Sim2Real 확장

### 5.1 확장 로드맵

```
TurtleBot3 (2D, 바퀴)
    │
    ▼
Drone (3D, 6-DOF, 4 rotors)
    │
    ▼
ICD 기반 인터페이스 설계
    │
    ▼
ROS2 노드 구현 (Mission Planner, FC Bridge, Sensor Fusion)
    │
    ▼
Isaac Sim Simulation (USD 드론, Physics, Action Graph)
    │
    ▼
Sim-to-Real 전환 (ros2_control HW Interface 교체)
    │
    ▼
통합 검증 (ICD → ROS2 → Sim → Real)
```

### 5.2 Isaac Sim에서의 TurtleBot3 vs Drone

| 항목 | TurtleBot3 | Drone (Quadrotor) |
|---|---|---|
| Dynamics | 2D diff-drive | 6-DOF rigid body |
| 제어 | cmd_vel (Twist) | thrust + attitude |
| 센서 | wheel encoder, IMU | IMU, GPS, LiDAR, Camera, Barometer |
| 시뮬레이션 | Isaac Sim 기본 | Isaac Sim + ROS2 Bridge |
| Sim→Real | trivial | ros2_control HW plugin |

### 5.3 TurtleBot3 → ICD 개념 연결

TurtleBot3의 `/cmd_vel`을 ICD 스타일로 정의하면:

```yaml
message: cmd_vel
id: 0x100
bus: ROS2_TOPIC
signals:
  - name: linear_x
    type: float64
    unit: m/s
    range: [-0.22, 0.22]    # TurtleBot3 Burger max speed
  - name: angular_z
    type: float64
    unit: rad/s
    range: [-2.84, 2.84]
  - name: linear_y
    type: float64
    unit: m/s
    range: [-0.0, 0.0]      # diff-drive는 lateral 불가
```

드론으로 확장하면 ControlCmd는 6-DOF + thrust가 됩니다.

## 6. 결론

- **1m 전진**은 단순해 보이지만, open-loop 제어의 한계를 드러냄
- **Odometry + EKF**로 센서 융합 → 더 정확한 상태 추정
- **ICD**는 복잡한 시스템(드론)에서 인터페이스를 체계적으로 관리
- **Isaac Sim Sim2Real**은 ICD 기반 ROS2 메시지를 시뮬레이션에서 검증 후 실제 하드웨어로 전환
